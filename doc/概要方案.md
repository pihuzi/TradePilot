一、三个项目分别借鉴什么
我检查了三个仓库。它们的设计重点不同，组合起来正好覆盖你提出的五个阶段。
参考项目	核心机制	建议借鉴的部分
Harvey（现已更名 Sellbird）	自主销售循环	企业发现、购买信号、决策人识别、邮件触达、回复分类、跟进、销售状态推进
OpenOutreach	B2B 线索发现与筛选	产品描述驱动 ICP、候选企业发现、AI 匹配判断、评分、付费数据补全、发送成本控制
First Customer Finder Skill	公开证据驱动的客户研究	公开需求信号、原始来源核验、证据归因、候选反馈、历史去重、搜索偏好迭代

1. Harvey：借鉴完整销售循环
Harvey 的核心不是简单生成开发信，而是让系统持续推进销售流程：
- Scout：发现和研究潜在客户。
- Writer：根据企业信号生成个性化邮件。
- Sender：管理待发送邮件、审批、发送限制。
- Handler：读取回复、判断意向、生成回复草稿。
- Analyst：统计转化表现，分析哪些线索和策略有效。
它还有一个值得重点借鉴的原则：自主运行不等于不受监督。

发送审批、每日发送上限、退信检测、停止跟进机制和全局停止开关都应成为系统能力。Harvey 仓库现已更名为 Sellbird，原链接会跳转到新项目。
GitHub+1

2. OpenOutreach：借鉴线索发现和付费资源控制
它的核心流程是：
产品描述 + 目标市场


候选企业发现

使用外部企业数据源，搜索阶段尽量低成本


ICP 匹配与理由解释

不只给出名单，还说明为什么这个客户值得开发


高匹配客户优先补全联系人

只对通过门槛的客户消耗付费查询额度


生成邮件并进入发送流程


特别值得借鉴的是它的成本控制方式：
- 免费或低成本发现尽可能多的候选企业。
- 先判断匹配度，再购买邮箱等付费数据。
- 不为低匹配度客户支付联系人查询费用。
- 付费动作有额度和成本边界。
它还将发现、筛选、数据补全和发送拆成独立模块，方便替换数据供应商。
GitHub+1

3. First Customer Finder：借鉴证据驱动的客户研究
这个项目的设计非常适合你的工业品获客场景。

它不只是搜索企业，而是寻找企业有公开理由需要某项产品或服务的证据。

例如：
- 企业官网明确展示某种生产工艺。
- 企业招聘相关生产、采购或工程岗位。
- 企业公开发布采购需求。
- 企业公开讨论某类技术问题。
- 企业发布扩产、设备升级或新产线信息。
每个候选客户都需要保留来源、日期、证据内容、判断依据和下一步建议。

它还区分了公开观察与推断，明确提醒：公开信号只能说明潜在需求，不能直接证明企业已经准备采购。反馈也会保存在本地历史中，用于后续调整搜索方向。

二、建议形成的最终业务架构
我建议将你的五个阶段定义为正式业务架构，今后所有 Skills、脚本、数据结构和测试用例都围绕它展开。
AI Overseas B2B Acquisition Agent
AI 海外 B2B 客户开发 Agent
01 · 目标市场与 ICP

明确产品能力、目标国家、行业、企业规模、采购角色，形成可执行的客户画像。
输出：ICP Profile


02 · 多源客户发现

通过企业目录、公司官网、公开需求、招聘、采购及业务变化信号发现候选企业。
输出：Candidate Companies


03 · 客户研究与资格判断

分析企业匹配度、采购链角色、需求证据、决策人线索，判断是否值得开发。
输出：Qualified Prospects


04 · 触达与跟进

生成个性化邮件、人工审批、发送、回复分类、跟进任务及销售阶段更新。
输出：Sales Conversations


05 · 获客数据与反馈闭环

客户去重、证据留存、转化统计、失败原因分析、ICP 和策略调整。
输出：Acquisition Intelligence


反馈回流至阶段 01

根据实际回复、有效商机、报价和成交结果，持续调整 ICP、信号权重和触达策略。

这里有一个重要调整：阶段 05 不应只是数据存储，而应该成为整个系统的学习和优化中心。

三、进一步拆解五个阶段的 Skills
不建议把每个功能都做成一个独立 Agent。第一阶段采用一个主控 Agent，配合 5 个主 Skills 和若干子 Skills。
主 Skill	子功能建议	主要交付结果
01-market-icp	产品分析、市场分析、ICP 构建、采购角色分析	ICP 配置文件
02-prospect-discovery	企业目录搜索、官网发现、公开需求搜索、信号发现、候选去重	企业候选库
03-prospect-research	官网研究、证据提取、需求判断、采购链分析、联系人线索、评分	客户研究报告
04-outreach-followup	邮件生成、邮件审批、发送、回复分类、跟进任务	销售活动记录
05-acquisition-intelligence	客户数据管理、证据归档、转化统计、反馈分析、ICP 调整	获客分析报告

每个 Skill 统一采用以下目录规范
skill-name/
├── SKILL.md
├── references/
│   ├── rules.md
│   ├── methodology.md
│   └── quality-criteria.md
├── scripts/
│   ├── validate.py
│   ├── process.py
│   └── export.py
├── templates/
│   ├── input.json
│   └── output.json
└── tests/
    └── test_cases.json


其中：
- SKILL.md：告诉 Agent 在什么条件下调用、怎么执行、什么时候停止。
- references/：保存业务知识、评分标准和判断规则。
- scripts/：处理去重、字段校验、评分计算和数据库操作。
- templates/：统一输入输出结构。
- tests/：保证每次修改 Skill 后，原有业务规则没有被破坏。
这与 Skills-First 的开发方式一致。主控 Agent 负责调度，Skill 负责业务判断，脚本负责确定性操作。

四、付费数据渠道：建议采用混合模式
我不建议坚持完全免费数据源。工业品 B2B 客户开发中，付费渠道可以显著改善企业发现、联系人补全和邮箱验证效率。

但要坚持一个原则：

先用低成本方式判断企业是否值得开发，再对高价值客户使用付费数据。

建议将数据渠道分成四层：
数据层	主要用途	渠道示例
免费公开信息	企业发现、官网验证、公开需求研究	Google、企业官网、行业协会、展会名录、招聘网站
企业数据库	企业规模、行业、企业名单补充	Apollo、Crunchbase
贸易与采购数据	进出口记录、采购关系、贸易流向	Volza、其他海关数据服务商
联系人数据	采购、工程、运营等角色识别及邮箱验证	Hunter、BetterContact

这些是候选供应商，不代表它们在所有国家、行业和企业规模上都有同样的数据覆盖。正式接入前，需要测试目标国家的数据质量、API 成本、许可范围和数据更新情况。
付费资源的调用策略
建议在系统中建立明确的付费调用规则：
操作	是否允许付费	触发条件
企业初步发现	优先免费	按 ICP 搜索
企业官网研究	优先免费	候选企业进入研究阶段
企业信息补全	可以付费	免费信息不足且企业匹配度较高
联系人查找	可以付费	企业通过资格判断
邮箱验证	可以付费	已确定目标联系人
低匹配客户补全	不允许	直接淘汰或暂存

可以将付费调用抽象成一个统一的工具：

data-enrichment-gateway

它负责：
1. 判断是否达到付费查询门槛。
2. 检查供应商额度和单次成本。
3. 选择合适的数据源。
4. 执行查询。
5. 记录数据来源、查询时间和费用。
6. 将结果写回客户档案。
这样未来即使替换 Apollo、BetterContact 或其他供应商，也不需要重写业务 Skill。

五、需要提前确定的四个系统级规则
这四点建议成为所有 Skills 都必须遵守的规则。

1. 事实、推断、未知必须分开

例如：
内容	状态
官网明确表示生产铝卷包装设备	已观察事实
企业可能需要无缝 PU 助卷带	待验证推断
是否正在寻找新的供应商	未知

Agent 不能把推断写成采购事实。

2. 企业和联系人分开管理

一个企业可能有采购、工程、生产、运营等多个角色。不能把企业匹配度直接等同于联系人匹配度。

3. 重要动作必须人工审批

至少包括：
- 修改 ICP 的关键约束。
- 通过高价值客户资格审核。
- 购买付费联系人数据。
- 首次向客户发送邮件。
- 处理高风险或复杂回复。
4. 每一次开发都要留下可追溯记录

包括企业 ID、证据来源、证据日期、评分依据、联系人来源、邮件版本、审批记录、发送结果、回复结果和后续跟进状态。

六、我建议的第一阶段开发顺序
不建议同时开发五个 Skills。先做一个最小可用闭环，再逐步扩展。
1. 第一步：01-market-icp
   
   建立产品资料输入规范和 ICP 输出结构。先解决“系统到底应该寻找什么样的客户”。
2. 第二步：02-prospect-discovery
   
   先接入公开搜索、企业目录和官网发现，形成稳定的候选企业列表。
3. 第三步：03-prospect-research
   
   建立公开证据研究、企业资格判断和匹配评分。这是整个产品最重要的价值环节。
4. 第四步：05-acquisition-intelligence
   
   先完成客户去重、证据保存和历史记录，避免后续数据无法积累。
5. 第五步：04-outreach-followup
   
   最后接入邮件发送、审批、回复分类和跟进机制，形成真正的销售循环。
先完成前四步的原因是：如果客户研究质量不可靠，自动发送只会放大错误；如果没有历史数据，后续也无法判断 ICP 是否有效。

八、最终建议
我认为这次调整是正确的。相比原来 00～18 的技术执行节点，新架构更容易向客户解释，也更容易逐步形成可销售的服务产品。

三个参考项目的借鉴关系可以固定为：
- Harvey / Sellbird：负责销售循环设计。
- OpenOutreach：负责线索发现、筛选和付费资源策略。
- First Customer Finder：负责公开证据研究和反馈机制。
但不建议直接把三个项目拼装起来。应该以 Ekko Studio 为运行基础，自主设计业务 Skills、数据结构和工具接口。

另外，商业化前需要分别核查许可：当前 Sellbird 仓库显示 AGPL-3.0，OpenOutreach 显示 Apache-2.0，First Customer Finder 显示 MIT。参考设计和复用代码是两回事，尤其是 AGPL 项目，不应在未评估义务前直接嵌入商业产品。

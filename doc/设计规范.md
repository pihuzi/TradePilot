## Skills 总体设计规范 V1.0

**文档版本：** V1.0  
**文档类型：** 总体技术设计规范  
**系统定位：** 面向中小制造企业的 AI 海外 B2B 客户开发 Agent  
**运行基础：** Ekko Studio / Agent Runtime  
**核心模式：** Skills-First、单主控 Agent、多 Skills 协作

# 一、项目概述

## 1.1 建设背景

中小制造企业在海外市场开发过程中，普遍存在以下问题：

1. 不清楚哪些海外国家和行业真正适合自己的产品。
2. 缺少有效的海外目标企业发现渠道。
3. 找到的企业数量不少，但难以判断是否具备真实业务匹配度。
4. 缺少对企业采购链、需求信号和决策角色的系统研究。
5. 海外客户开发依赖人工搜索、信息整理和邮件撰写，效率较低。
6. 客户开发过程缺乏统一记录，无法根据实际转化结果持续优化。

本项目建设一个以 AI Agent 为核心的海外 B2B 客户开发系统。

系统根据企业提供的产品资料和目标市场要求，自动完成：

- 目标市场与 ICP 定义
- 多源海外企业发现
- 企业研究与资格判断
- 客户触达与跟进
- 获客数据管理与反馈优化

系统不以批量生成企业名单为目标，而是帮助企业发现、研究和筛选有明确业务匹配依据的海外潜在客户。

## 1.2 建设目标

建设一个可配置、可扩展、可自托管的 AI 海外 B2B 客户开发 Agent。

核心目标：

1. 将海外客户开发流程标准化。
2. 将企业产品能力转化为可执行的 ICP。
3. 利用多源公开信息发现潜在客户。
4. 使用公开证据支持企业研究和资格判断。
5. 通过人工审批控制对外触达风险。
6. 通过客户反馈不断调整 ICP 和开发策略。
7. 控制外部 API、企业数据和联系人数据的使用成本。

## 1.3 产品定位

本系统不是简单的 AI 搜索工具，也不是传统 CRM。

它定位为：

**以企业产品能力为起点，以 ICP 为筛选标准，以公开证据为研究依据，以销售反馈为优化信号的 AI 海外客户开发 Agent。**

核心价值：

- 找到可能适合的企业。
- 说明为什么适合。
- 提供支持判断的证据。
- 找到可能参与采购决策的角色。
- 辅助完成个性化触达。
- 根据实际结果优化后续开发。

# 二、总体业务架构

系统采用五阶段业务架构。

## 2.1 五阶段业务流程

### 阶段 01：目标市场与 ICP

**目标：** 明确系统应该寻找什么样的海外客户。

主要输入：

- 产品资料
- 产品应用场景
- 产品技术参数
- 目标国家或地区
- 目标行业
- 企业规模
- 采购角色
- 供应商能力与限制

主要功能：

1. 产品资料解析。
2. 产品应用场景识别。
3. 目标国家分析。
4. 目标行业分析。
5. 企业类型定义。
6. 企业规模定义。
7. 采购链角色分析。
8. ICP 生成与确认。

主要输出：

- Product Profile
- Market Profile
- ICP Profile
- Target Role Profile

质量要求：

- 区分已确认产品信息和待确认信息。
- 不将产品应用可能性直接认定为市场需求。
- 不擅自扩大产品适用范围。
- ICP 必须由用户确认后进入正式发现阶段。

### 阶段 02：多源客户发现

**目标：** 根据 ICP 寻找符合条件的海外候选企业。

数据来源：

- 搜索引擎
- 企业目录
- 行业协会
- 展会参展商名录
- 企业官方网站
- LinkedIn 企业页面
- 公开采购需求
- 企业招聘信息
- 企业扩产、设备升级和业务变化信息
- 付费企业数据库
- 贸易与海关数据

主要功能：

1. 根据 ICP 生成搜索策略。
2. 多渠道搜索候选企业。
3. 获取企业名称、官网、国家、行业等基础信息。
4. 识别公开业务信号。
5. 企业名称和域名标准化。
6. 企业候选去重。
7. 记录发现来源。

主要输出：

- Candidate Company List
- Discovery Evidence
- Discovery Source Records

质量要求：

- 企业必须具备可追溯来源。
- 不能将搜索结果标题直接视为已验证企业事实。
- 不同数据源的企业记录需要统一标准化。
- 不允许仅凭关键词相似就判定企业匹配。
- 发现阶段不直接执行外部邮件触达。

### 阶段 03：客户研究与资格判断

**目标：** 判断候选企业是否值得开发。

主要研究内容：

1. 企业身份和经营范围。
2. 产品及业务匹配度。
3. 企业生产能力和业务模式。
4. 企业在采购链中的角色。
5. 产品需求相关证据。
6. 采购、扩产、招聘、设备升级等公开信号。
7. 可能参与采购决策的联系人及岗位线索。
8. 企业真实性和信息可信度。

主要功能：

- 企业官网研究。
- 企业产品与业务分析。
- ICP 匹配评分。
- 采购链角色判断。
- 公开需求证据提取。
- 联系人线索发现。
- 信息交叉验证。
- 客户资格审核。
- 客户研究报告生成。

主要输出：

- Prospect Research Report
- ICP Match Score
- Evidence Records
- Buying Role Analysis
- Contact Leads
- Qualification Decision

质量要求：

- 每项重要判断尽量关联原始证据。
- 证据事实、分析推断和未知信息必须分开。
- 不允许虚构企业采购意图。
- 不允许把企业员工、招聘岗位或普通管理人员直接认定为采购决策人。
- 联系人身份及联系方式必须有来源。
- 关键客户资格判断应支持人工审核。

### 阶段 04：触达与跟进

**目标：** 将通过资格判断的客户转化为真实销售沟通机会。

主要功能：

1. 目标联系人选择。
2. 企业背景和需求信息整理。
3. 个性化开发邮件生成。
4. 邮件内容质量检查。
5. 人工审批。
6. 邮件发送。
7. 回复信息获取。
8. 回复意向分类。
9. 回复草稿生成。
10. 跟进任务生成。
11. 销售阶段更新。
12. 停止联系和退订管理。

主要输出：

- Outreach Draft
- Approval Record
- Email Activity
- Reply Classification
- Follow-up Task
- Sales Status

质量要求：

- 首次发送必须经过人工审批。
- 邮件内容必须基于真实企业信息。
- 不得编造双方曾有过的业务联系。
- 不得把推断需求写成确定采购需求。
- 必须记录邮件发送和回复状态。
- 退订、拒绝联系和明确不感兴趣的客户必须进入停止联系状态。
- 遵守目标地区适用的隐私、反垃圾邮件和营销通信规定。

### 阶段 05：获客数据与反馈闭环

**目标：** 通过客户开发结果优化整个系统。

主要功能：

1. 企业信息去重和归档。
2. 客户证据保存。
3. ICP 版本管理。
4. 客户开发活动记录。
5. 邮件回复统计。
6. 有效商机统计。
7. 报价和成交结果统计。
8. 无效客户原因分析。
9. 不同数据源效果分析。
10. ICP 调整建议。
11. 搜索策略优化。
12. 评分规则优化。

主要输出：

- Acquisition Database
- Conversion Report
- Source Performance Report
- ICP Optimization Report
- Strategy Feedback

质量要求：

- 每次客户开发活动必须能够关联企业和 ICP 版本。
- 统计指标必须明确计算口径。
- 不允许仅根据单个客户结果自动修改 ICP。
- ICP 和评分规则调整应保留版本及变更记录。
- 重要规则调整需要人工确认。

## 2.2 业务闭环

系统形成以下循环：

目标市场与 ICP  
→ 多源客户发现  
→ 客户研究与资格判断  
→ 触达与跟进  
→ 获客数据与反馈  
→ ICP 和开发策略优化  
→ 新一轮客户发现

其中，阶段 05 是反馈中心，负责将实际客户开发结果反馈给阶段 01、02、03 和 04。

# 三、总体技术架构

## 3.1 架构设计原则

1. 不开发独立 Web 前端。
2. 以 Ekko Studio / Agent Runtime 作为运行基础。
3. 以 Skills 承载业务流程和判断规则。
4. 以 Python Scripts 承担确定性处理任务。
5. 以 API / MCP / 外部工具连接数据源和业务系统。
6. 以 SQLite 管理结构化业务数据。
7. 以 Markdown 管理报告、规则和知识资料。
8. 各业务 Skill 独立开发、独立测试、可替换和可扩展。

## 3.2 总体架构分层

### 第一层：用户交互层

用户通过 Agent 对话提交任务，例如：

- 分析一款工业输送带产品。
- 寻找德国输送带经销商。
- 研究某个候选企业。
- 生成客户开发邮件。
- 查看本月客户开发结果。

交互形式：

- 自然语言任务。
- Markdown 报告。
- CSV 数据文件。
- JSON 结构化结果。

### 第二层：主控调度层

由 Ekko Studio / Agent Runtime 提供运行环境。

主要职责：

- 接收用户任务。
- 识别任务类型。
- 选择对应 Skill。
- 管理 Skill 调用顺序。
- 传递上下文和结构化参数。
- 检查阶段完成状态。
- 处理人工审批。
- 返回执行结果。

主控 Agent 不负责取代所有业务 Skills，而是负责任务分发和流程协调。

### 第三层：业务 Skills 层

包括五个主 Skills：

1. market-icp
2. prospect-discovery
3. prospect-research
4. outreach-followup
5. acquisition-intelligence

每个主 Skill 可以包含若干子功能，但不要求每个子功能都成为独立 Skill。

### 第四层：工具与脚本层

负责提供确定性的执行能力：

- 搜索 API。
- 网页抓取。
- 官网内容提取。
- PDF 解析。
- 企业数据 API。
- 贸易数据 API。
- 联系人查找 API。
- 邮箱验证 API。
- 邮件 API。
- SQLite 数据访问。
- Python 数据处理脚本。

### 第五层：数据与知识层

结构化数据：

- SQLite

非结构化数据：

- Markdown
- JSON
- CSV
- 企业研究报告
- 原始证据归档

知识管理：

- Obsidian

## 3.3 核心技术关系

Ekko Studio / Agent Runtime  
负责运行和调度。

Skills  
负责业务流程、分析方法和判断规则。

Python Scripts  
负责标准化、去重、评分、验证和数据处理。

外部 API / MCP  
负责获取外部数据和执行外部操作。

SQLite  
负责企业、联系人、证据、触达和反馈数据管理。

Obsidian  
负责业务知识、开发规范、研究方法和项目文档管理。

# 四、Skills 总体设计

## 4.1 Skill 命名规范

采用统一命名：

01-market-icp  
02-prospect-discovery  
03-prospect-research  
04-outreach-followup  
05-acquisition-intelligence

统一原则：

- 使用英文小写。
- 使用连字符分隔。
- 编号与业务流程一致。
- 一个主 Skill 对应一个明确业务阶段。
- 子功能优先放在主 Skill 内部，避免过度拆分。

## 4.2 Skill 目录规范

每个 Skill 采用统一目录结构：

```text
skill-name/
├── SKILL.md
├── references/
│   ├── rules.md
│   ├── methodology.md
│   └── quality-criteria.md
├── scripts/
│   ├── validate.py
│   ├── process.py
│   └── export.py
├── templates/
│   ├── input.json
│   └── output.json
└── tests/
    └── test_cases.json
```

目录说明：

| 目录 | 用途 |
|---|---|
| SKILL.md | Skill 的入口说明、执行流程和调用规则 |
| references | 业务知识、研究方法、评分规则和质量标准 |
| scripts | 确定性处理脚本 |
| templates | 统一输入输出格式 |
| tests | 测试数据和验收用例 |

具体 Skill 可以按实际需要增减文件，但必须保留统一入口和接口规范。

# 五、统一输入输出规范

## 5.1 基本原则

所有 Skills 之间通过结构化数据传递结果。

统一要求：

- 使用 JSON 作为主要交换格式。
- 使用唯一 ID 关联企业、联系人和证据。
- 每个输出包含状态、时间和数据来源。
- 不允许只输出无法被后续 Skill 使用的自然语言。
- Markdown 报告用于展示，JSON 用于系统流转。

## 5.2 统一任务结构

每次 Skill 执行使用统一任务信息：

```json
{
  "task_id": "TASK-2026-000001",
  "skill_name": "02-prospect-discovery",
  "task_status": "running",
  "created_at": "2026-11-26T10:00:00+08:00",
  "supplier_id": "SUP-000001",
  "icp_id": "ICP-000001",
  "input_reference": [],
  "output_reference": [],
  "approval_required": false
}
```

## 5.3 统一企业数据结构

```json
{
  "company_id": "COM-000001",
  "company_name": "Example Industrial Co.",
  "country": "Germany",
  "website": "https://example.com",
  "industry": [],
  "company_type": [],
  "employee_range": null,
  "business_description": "",
  "icp_match_score": null,
  "qualification_status": "pending",
  "discovery_sources": [],
  "evidence_ids": [],
  "created_at": "",
  "updated_at": ""
}
```

## 5.4 统一证据数据结构

```json
{
  "evidence_id": "EVD-000001",
  "company_id": "COM-000001",
  "evidence_type": "business_activity",
  "claim": "企业公开展示相关生产业务",
  "source_url": "https://example.com",
  "source_type": "official_website",
  "published_at": null,
  "collected_at": "2026-11-26T10:00:00+08:00",
  "evidence_excerpt": "",
  "evidence_status": "observed",
  "confidence": "high",
  "related_icp_criteria": [],
  "verification_status": "unverified"
}
```

证据状态：

- observed：来源直接展示的内容。
- inferred：根据证据作出的分析推断。
- unknown：目前无法确认。
- contradicted：发现相反证据。

可信度不能替代来源验证状态，两者需要分别记录。

## 5.5 统一联系人数据结构

```json
{
  "contact_id": "CON-000001",
  "company_id": "COM-000001",
  "full_name": null,
  "job_title": "Purchasing Manager",
  "department": "Procurement",
  "role_type": "buyer",
  "email": null,
  "linkedin_url": null,
  "source_url": "",
  "verification_status": "unverified",
  "contact_status": "identified"
}
```

联系人状态：

- identified：发现联系人线索。
- verified：身份和相关信息得到核验。
- unreachable：无法建立联系。
- do_not_contact：禁止继续联系。

# 六、数据存储设计

## 6.1 数据存储方案

第一阶段采用 SQLite。

原因：

- 部署简单。
- 运行成本低。
- 不需要独立数据库服务。
- 适合单用户和小规模试点。
- 后续可以迁移到 PostgreSQL。

## 6.2 核心数据表

| 数据表 | 主要用途 |
|---|---|
| suppliers | 供应商信息 |
| products | 产品能力信息 |
| market_profiles | 市场研究结果 |
| icp_profiles | ICP 配置及版本 |
| companies | 企业基础信息 |
| company_aliases | 企业别名和标准化信息 |
| contacts | 联系人信息 |
| evidence_records | 企业证据 |
| discovery_runs | 企业发现任务 |
| research_reports | 企业研究报告 |
| qualification_records | 客户资格判断 |
| outreach_campaigns | 客户开发活动 |
| email_activities | 邮件发送和回复记录 |
| followup_tasks | 跟进任务 |
| approval_records | 人工审批记录 |
| data_source_logs | 数据源调用记录 |
| cost_records | API 和数据查询费用 |
| conversion_events | 转化事件 |
| system_feedback | 反馈和规则优化记录 |

## 6.3 数据管理原则

1. 企业采用唯一 company_id。
2. 联系人必须关联 company_id。
3. 证据必须关联企业或联系人。
4. 触达记录必须关联企业和联系人。
5. 每次 ICP 调整必须生成新版本。
6. 数据源调用必须记录时间和成本。
7. 不允许直接覆盖重要历史记录。
8. 关键状态变化需要记录操作日志。

# 七、外部工具与数据源设计

## 7.1 工具接入原则

不将业务 Skills 与特定数据供应商绑定。

通过统一工具接口调用不同数据源。

例如：

```text
company_search()
website_fetch()
webpage_extract()
company_enrichment()
trade_data_search()
contact_search()
email_verify()
email_send()
email_reply_fetch()
```

不同供应商实现对应接口。

## 7.2 数据源分类

### A. 公开信息源

- Google / Bing 等搜索引擎
- 企业官方网站
- 行业协会
- 展会名录
- 企业公开目录
- LinkedIn 公开企业信息
- 招聘网站
- 公开采购平台

### B. 企业数据源

- Apollo
- Crunchbase
- 其他企业数据库

### C. 贸易数据源

- Volza
- 其他海关和进出口数据服务

### D. 联系人数据源

- Hunter
- BetterContact
- 其他联系人数据服务

### E. 触达工具

- 邮件服务商 API
- SMTP
- 其他合规的客户沟通渠道

## 7.3 付费 API 管理

付费 API 必须通过统一的数据调用网关。

主要职责：

1. 检查调用条件。
2. 检查剩余额度。
3. 评估查询必要性。
4. 选择数据供应商。
5. 记录调用费用。
6. 保存数据来源。
7. 检查返回数据质量。

建议初期策略：

- 企业发现优先使用公开数据。
- 企业研究优先使用官方网站。
- 高匹配客户才调用企业补全 API。
- 通过资格审核后再查询联系人。
- 需要发送前再进行邮箱验证。
- 不为低匹配客户购买联系人数据。

# 八、业务审批与安全控制

## 8.1 人工审批节点

以下操作需要人工确认：

| 操作 | 审批要求 |
|---|---|
| ICP 正式发布 | 必须 |
| 购买高成本企业数据 | 达到成本阈值时审批 |
| 购买联系人数据 | 必须满足资格门槛，按成本规则审批 |
| 高价值客户资格确认 | 建议 |
| 首次开发邮件发送 | 必须 |
| 重要回复内容发送 | 必须 |
| ICP 规则重大调整 | 必须 |
| 批量发送任务 | 必须 |

## 8.2 自动化边界

可以自动执行：

- 公开网页搜索。
- 企业信息提取。
- 企业名称标准化。
- 企业去重。
- 证据整理。
- 规则评分。
- 报告生成。
- 邮件草稿生成。
- 回复初步分类。
- 跟进任务建议。

默认需要审批或人工确认：

- 购买付费数据。
- 修改正式 ICP。
- 发送外部邮件。
- 处理高风险回复。
- 删除关键业务数据。
- 批量触达。

## 8.3 证据与合规要求

- 保留原始 URL 和采集时间。
- 尽可能保留页面标题和必要的证据摘要。
- 尊重网站服务条款、访问限制和数据许可。
- 不绕过访问控制或反爬机制。
- 对个人数据实施最小化收集。
- 对退订和拒绝联系请求提供停止机制。
- 按目标市场适用法律处理个人数据和营销联系。

# 九、成本控制设计

## 9.1 成本控制原则

采用分层查询策略：

第一层：免费发现  
第二层：低成本研究  
第三层：付费企业信息补全  
第四层：付费联系人查询  
第五层：邮箱验证与触达

## 9.2 付费查询门槛

建议为每个候选企业设置资格状态：

- discovered：已发现。
- researching：研究中。
- qualified：通过资格判断。
- rejected：不符合要求。
- pending_review：等待人工审核。

只有达到设定条件的企业，才能进入付费联系人查询。

## 9.3 成本统计

每次 API 调用记录：

- provider
- API name
- company_id
- task_id
- request_time
- estimated_cost
- actual_cost
- result_status

系统应支持统计：

- 单个候选企业发现成本。
- 单个有效客户研究成本。
- 单个有效联系人获取成本。
- 单个有效回复成本。
- 单个有效商机成本。

# 十、质量评估与测试规范

## 10.1 Skill 测试原则

每个 Skill 必须具备：

1. 正常输入测试。
2. 缺失信息测试。
3. 错误数据测试。
4. 来源不可访问测试。
5. 低置信度判断测试。
6. 重复数据测试。
7. 异常中断测试。
8. 输出格式验证。

## 10.2 核心质量指标

### 市场与 ICP

- ICP 字段完整率。
- ICP 规则可执行率。
- 用户确认率。

### 客户发现

- 候选企业有效率。
- 企业去重准确率。
- 企业官网可验证比例。
- 单个候选企业发现成本。

### 客户研究

- 证据来源完整率。
- 关键判断证据覆盖率。
- ICP 匹配准确率。
- 客户资格审核通过率。
- 联系人信息核验率。

### 触达与跟进

- 邮件审批通过率。
- 邮件送达率。
- 回复率。
- 正向回复率。
- 跟进任务完成率。

### 反馈闭环

- 有效商机转化率。
- 不同数据源的有效客户贡献。
- 不同 ICP 版本的转化表现。
- 单个有效商机获取成本。

所有指标必须统一统计口径，不能把候选企业数量直接当作有效客户数量。

## 10.3 测试验收要求

每个 Skill 上线前必须通过：

- 输入输出结构校验。
- 业务规则测试。
- 质量门槛测试。
- 错误处理测试。
- 人工审批测试。
- 成本记录测试。
- 真实业务案例测试。

# 十二、项目开发约束

1. 第一阶段不开发独立 Web 前端。
2. 第一阶段不建设复杂多 Agent 架构。
3. 不将所有业务功能写进一个超长 SKILL.md。
4. 不允许 Skills 之间使用不受约束的自然语言作为唯一数据接口。
5. 不允许没有证据来源的企业判断进入正式客户库。
6. 不允许未经审批自动发送首次开发邮件。
7. 不允许低匹配客户无条件消耗付费 API 额度。
8. 不允许将公开需求信号等同于真实采购意向。
9. 不将特定数据供应商写死在业务流程中。
10. 不直接复制参考项目代码，必须先核查许可证和商业使用义务。
11. Skills 应尽量与运行平台解耦，便于后续迁移。
12. 重要业务规则必须通过脚本或测试进行验证，不能只依赖 Agent 的上下文记忆。

# 十三、V1.0 交付标准

V1.0 的目标不是实现完全自主的销售机器人，而是实现一个稳定、可验证、可持续迭代的海外 B2B 客户开发工作流。

必须具备：

- 五阶段业务架构。
- 五个主 Skills 的统一规范。
- 标准化输入输出结构。
- 企业和联系人数据模型。
- 公开证据记录机制。
- ICP 匹配与资格判断机制。
- 付费数据调用控制机制。
- 人工审批机制。
- 客户数据持久化机制。
- 基础质量测试机制。

最终验收场景：

用户输入一家制造企业的产品资料和目标市场要求，系统能够：

1. 分析产品能力。
2. 建立 ICP。
3. 发现候选海外企业。
4. 研究企业业务及需求相关证据。
5. 判断企业匹配度。
6. 输出符合资格要求的潜在客户。
7. 为目标联系人生成个性化开发邮件。
8. 在人工审批后执行触达。
9. 记录回复和跟进情况。
10. 根据客户开发结果生成优化建议。

**V1.0 核心验收标准：系统能够解释每一个客户为什么被发现、为什么被推荐、依据是什么，以及下一步应该做什么。**
